## Canonical conformance

`app/PromptOps/CanonicalContracts.php` implements prompt/schema digests, the resolver's ordered approval/window/hash refusals and the promotion-report aggregation. The six canonical roles remain unchanged. Their original generic templates and durable-store simulator are fixture inputs, not production agents or a durable prompt database. The resolver retains upstream string-window comparisons and first matching array-store semantics. It never invokes a model, callback, tool or network.

Hash domain is deliberately bounded: ASCII object keys, integer constraints, booleans, null, Unicode strings, nested objects and lists. Empty JSON objects must remain `stdClass`; unsupported keys/floats refuse explicitly. This matches the imported fixture/product schema domain without claiming a general JavaScript JSON-number/Unicode-key port. Canonical schema hashing compares version/schema/output-contract identity; it does not validate a model response.

`tests/fixtures/promptops_canonical_vectors.json` was generated by executing the actual canonical TypeScript functions using `promptops-golden-generator.mts`: 23 resolver results, 6 promotion reports and 3 schema hashes, including Swedish/Unicode values, nested empty objects, key ordering, missing/draft/revoked/expired records, tampering, duplicate roles and strict fallback refusal. Regenerate with the canonical repository's pinned TypeScript runner and explicit canonical/output paths. The executable source hashes must match the manifest before accepting new vectors.

## Deployment-authored Monitor roles

The private immutable file `app/PromptOps/bundles/2026-09-27.monitor.v1.json` contains new deployment-specific roles, not additional canonical role registrations:

- `P01_SIGNAL_CLASSIFIER`: source-bound before/after observations, canonical P01 signal class, tenant-context relevance hypotheses and explicit uncertainty.
- `BATTLECARD_GENERATOR`: cited internal draft, exact five P01 battlecard content fields and per-field citation lists; recommends only configured P04 organization role classes, not permissions, individuals or memberships.
- `MONITOR_REVIEW_CRITIC`: independent candidate challenge; an acceptable result means only `ACCEPT_FOR_HUMAN_REVIEW`, never M07 approval, Arbiter verdict or release.
- `MONITOR_ROUTING_CRITIC`: a separate review of the exact proposed P04 routing, configured organization role, current source release and summary. It uses its own version/binding/schema identities and does not reuse the battlecard critique as a new sensitivity assessment.

All instructions separate untrusted source/profile/candidate content from instructions, preserve Swedish qualifiers and factual uncertainty, prohibit scope expansion and external actions, distinguish owner-supplied context from observations, and require exact supplied evidence IDs. The schemas are strict, versioned objects; all properties are required and extra properties forbidden.

`ProductPromptPack::resolve($role): Outcome` returns the exact instructions/schema and role/version/binding/schema IDs plus canonical hashes. Output is `approval_status=DRAFT`, `activation_status=INACTIVE`, `evaluation_status=OFFLINE_CONTRACT_TESTED`, `model_evaluated=false`, `execution_authorized=false`. Resolution is available for request inspection and synthetic fixtures. The provider must compare the full result with a fresh trusted pack resolution; a self-recomputed digest is not an approved prompt. There is no mutable runtime prompt editor or hidden activation switch.

## Candidate checks and limits

After the provider's strict schema validation, `CandidateChecks::validate($candidate, $resolvedPrompt, $context)` accepts the full ContextEnvelope result. It checks evidence-reference membership and basis, source-versus-owner-context separation, required hold on declared injection, status consistency, cited battlecard fields and non-authoritative critic outcomes. It returns `semantic_truth_verified=false` and `human_review_required=true` even on success.

These checks cannot prove that a cited text entails natural-language claims, detect every injection, measure Swedish comprehension, or establish independence merely from a role name. The 24 offline cases are manually authored contract examples, not model generations, eval performance scores or provider readiness. Real model evaluations on normal, ambiguous, adversarial and Swedish examples, independent prompt review, provider readiness and explicit activation evidence remain required before a live model workflow. Native execution stays refused while the pack is inactive. A model-produced candidate still passes existing M04/M05/M07/M08/M10 and source-use release checks; no candidate helper writes a release.

## Approval and evaluation (completion plan P01/P02)
