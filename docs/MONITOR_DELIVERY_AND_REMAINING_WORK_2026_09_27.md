# Bounded Monitor delivery and remaining work

27 September 2026 — implementation scope and claim boundary. Exact commits, merge outcomes, test counts and deployment status belong to the independently recorded final implementation/qualification report in the operator evidence workspace. This document deliberately does not substitute candidate results for deployed-host evidence.

## Purpose and delivered path

The requested SME MVP is an agent-assisted internal competition-monitoring workflow: use the owner's admitted company profile to explain why an observed competitor change may matter, produce a cited battlecard, challenge that draft, obtain a human decision, and route the released intelligence to an explicitly configured internal role. A console populated with manually seeded results would not fulfil that purpose by itself.

The implementation now composes this bounded path using the existing owners:

| Stage | Implemented behavior and boundary |
| --- | --- |
| Approved company context | Private M05 uploaded capture with matching retained bytes; explicitly tenant-provided and unverified. It supplements the source comparison and cannot replace it. |
| Approved source capture | Existing P01/M05/M06/M01 capture and source-policy gates, with actual before/after snapshot identities. Retained comparison proof and body use respect the selected retention policy. No arbitrary crawl frontier. |
| Change detection | Deterministic comparison bound to captured provenance. An absent retained comparison basis remains unknown; caller-supplied text cannot rewrite the classification. |
| Interpretation | Versioned `P01_SIGNAL_CLASSIFIER` instructions and strict schema; observations and relevance hypotheses cite selected evidence and preserve uncertainty. |
| Draft | `BATTLECARD_GENERATOR` consumes the bound classifier candidate and selected profile/source context. Its internal-role recommendation is empty or the single server-verified configured target. It creates no membership or delivery right. |
| Draft challenge | A separately assigned `MONITOR_REVIEW_CRITIC` produces an advisory structured result. A model recommendation cannot approve itself or issue a release. |
| Human P01 decision | The operator inspects exact requests/candidates and records an original assessment against the current review digest. Existing M07/M08/M10 and P01 release checks determine whether an internal briefing can be released. |
| Routing proposal | Existing P04 composition creates the exact proposed summary for the configured organization role, tied to the current P01 source release. |
| Routing challenge and decision | The fourth role, `MONITOR_ROUTING_CRITIC`, reviews that exact package and policy. A separate human decision follows; current package/authority is checked again before P04 admission and internal release. |
| Inspection and replay | The protected workbench shows prompts, exact API bodies, request/candidate identities, reviews and run history. Replay does not fetch or invoke again. Current M10 reliance is displayed separately from historical completion. |

The runner advances one step at a time, binds model submissions to the request just displayed, records scoped private artifacts and applies a lifetime mission budget of at most four admitted reserved model attempts. Baseline, no-change, hold, failure and stop are distinct terminal outcomes. An interrupted or ambiguous attempt requires reconciliation; automatic retries, automatic budget resets and autonomous scheduling are absent.

## Reconciliation with canonical Allfather

The baseline canonical source comparison found no newer runtime implementation in the relevant directories between the original projection pin and the initially inspected canonical main. The work therefore did not assume that a broad pin advance would supply missing behavior. The base `upstream.lock.json` pin remains unchanged; selected extensions and their source hashes are recorded separately in the reconciliation documents.

The selected canonical repairs address source-contract reference persistence, capture/comparison provenance and retention, admitted owner-context lineage with uncertainty and separate internal-only source contribution, and repeatable scoped P01 registration. The context extension is deliberately restricted to diff-backed Monitor signals; it does not silently alter candidate-backed M15 admission. Registration reuses compatible global tool/tier definitions, requires any shared runtime mapping to be active and scopeless, and records scoped setup receipts rather than guessing how to adopt older registrations. The final review/merge evidence identifies the exact repaired heads.

The PHP PromptOps import is a selective port of pure hashing, resolution and promotion-check contracts, with canonical conformance fixtures. The four actual product prompts are new deployment-authored content, not the canonical six advisory fixture roles and not a wholesale M13/M14 implementation. Provider/context/workflow seams and the workbench are explicitly reconciled local composition additions. They do not replace the M01–M12/M15/M16 authority owners or claim full feature parity with the larger platform.

The owner authorized this bounded implementation and its reviewed merge workflow. That authorization does not turn a merge, fixture pass or stored configuration into approval for live source access, model execution, customer output, consequential external action or production launch.

## What is qualified by fixtures

Offline prompt cases are manually authored examples. Strict schema checks, reference membership, predecessor/context digests, current source-policy checks and governed database receipts establish mechanical contracts; they do not establish factual entailment or real model quality. The local connected fixtures drive real services/database transitions with synthetic source/model transports, explicit independent critic assignment and separately recorded synthetic human decisions. These show that the components can be composed, not that a live competitor observation or live model response was reviewed.

The HTTP checks exercise the real Kernel, authentication/session scope, workspace choice, body-only mutation inputs, CSRF, private request/candidate access and actual inactive/stopped service behavior. The synthetic browser inspection covers the request, review and refusal layouts. Exact receipts and their limitations are filed with the final report. Neither an in-process Kernel test nor a local static browser view is a Loopia host, Apache or deployed-release qualification.

Native execution remains inactive at the default factory and prompt bindings. There is no production activation entrypoint that this delivery instructs an operator to turn on. Generic provider telemetry without the attempt's fixture/live provenance is not evidence of a real API call. No live source, provider call, scheduler, customer delivery or production action is implied by this document.

## Remaining work, in dependency order

1. **Qualify and deploy the exact candidate inertly.** Review the final source/extension record and qualification receipts, prepare the exact release, then complete the staging deployment, migration and real-host requalification process. Repeat the relevant HTTP/security/browser checks, evidence filing and rollback/restore qualification for that release. Earlier staging qualification remains evidence for its earlier exact release only. Preserve the recorded shared-host deviation; it does not establish production isolation.
2. **Review and evaluate the product prompts before native use.** Evaluate the actual model against normal, ambiguous, Swedish and adversarial source/profile examples. Inspect factual/inference separation, citations, uncertainty, before/after completeness, target selection and injection handling. Record reviewed prompt/version/schema identities, failures and acceptance criteria. Offline fixture success alone cannot supply that approval.
3. **Implement the bounded activation entrypoint.** Native execution needs a separately reviewed configuration/authorization path that binds approved prompt versions, source scope, operator/workspace, model, transport, credential identity, limits and an explicit owner decision. The current inactive factory and draft prompt state must continue to fail closed until that path is implemented and approved. Do not replace the gap with an untracked flag change or direct transport call.
4. **Prepare the first real mission.** Confirm the admitted company-profile bytes, exact public source URLs, terms/use/retention evidence, intended internal target and fresh P01/P04 policies. Verify provider authentication and sufficient funded quota through a bounded approved check. Keep credentials private and distinct from request previews and evidence reports. Obtain explicit owner GO for this source/model scope and budget; implementation/merge authorization is not that GO.
5. **Run a manual bounded ROAD_TEST_001.** Start with the approved P01-focused mission, inspect each exact request, and perform both human reviews. Record real capture lineage, actual provider attempt/result identities, uncertainty, refusal behavior, internal release evidence and stand-down. Reconcile interruption or quota failures without automatic retries or new identities that evade the original budget. A live diagnostic alone does not prove the complete mission.
6. **Consider scheduling after the manual mission is qualified.** Scheduler transport/activation, recurring mission authority, renewal budgets, observation cadence, failure notification and stand-down require their own bounded design and evidence. The runner currently has no scheduler activation and does not replenish a consumed mission budget.
7. **Treat production as a separate promotion.** Resolve the required hosting/isolation boundary, distinct production secrets and backup/restore requirements, production identity/visibility policy and explicit production/customer-output GO. An accepted inert-staging shared-host deviation cannot be inherited as production assurance.

Broader self-service onboarding, source/prompt administration screens, richer console coverage and the P02/P03/P05 product expansion can follow the bounded Monitor path. Full adaptive M13/M14, general-purpose Fetch/Port orchestration, additional product agents and consequential external-action surfaces are outside this delivery. They are not prerequisites to be silently added to a first bounded internal Monitor mission, and they are not claimed complete here.
